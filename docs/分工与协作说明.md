## 3. 跨域契约（避免互相改代码）

三人并行开发最容易冲突的地方是"公共字段与公共能力"，因此先由组长定死以下契约：

| 契约 | 内容 | 变更方式 |
|---|---|---|
| 主键 | 32 位字符串雪花号，前缀区分实体（`BAT`/`EVT`/`COD`/`USR`/`FRM`） | 只增不改 |
| 响应体 | `{code, message, data}`，分页 `{items, total, page, size}` | 只增字段 |
| 错误码 | `40001 / 40101 / 40301 / 40401 / 40901 / 42201 / 42202 / 50001 / 50002` | 新增需在 `core/errors.py` 登记 |
| 鉴权 | `Authorization: Bearer <JWT>`，`require_roles(...)` 守卫 | 不变 |
| 用户与产地 | `User`、`Farm` 表字段 | 王×× 只新增表/字段，不改既有语义 |
| 交易联动 | 下单前查 `trace_code.status == active` | 李×× 只读 trace_code，不写 |

**域间调用只走业务层**：交易域需要校验码状态时，调用 `TraceService.resolve_code_for_trade()`，
不直接写 SQL 查 `trace_code`，避免表结构变更时牵连两个域。

## 4. 分支与提交规范

| 分支 | 用途 | 保护策略 |
|---|---|---|
| `main` | 可演示的稳定版本 | 受保护，只允许 PR 合并，需 1 人 approve + CI 通过 |
| `feat/trace-chain` | 溯源链域 | 组长自用，按 UC 小步提交 |
| `feat/trade` | 交易域 | 李×× |
| `feat/identity-ops` | 用户与运营域 | 王×× |
| `fix/<问题>` | 缺陷修复 | 从 `main` 拉出，修完合回 |

提交信息用 Conventional Commits，类型限定 `feat / fix / test / docs / refactor / chore`，
作用域写业务域，例如：

```
feat(trace): 批次建档与创世记录同事务落库
fix(trace): 并发追加序号冲突改为原子自增 + 唯一索引兜底
test(trace): 补齐尾部截断检测用例
docs(trace): 补充 UC-01~UC-05 用例规格
```

**粒度要求**：一次提交只做一件事；数据库结构变更必须单独一个提交并附 `sql/` 迁移脚本。

## 5. PR 与评审

1. 从自己的 `feat/*` 分支开 PR 到 `main`，标题格式 `feat(trace): 一句话说明`；
2. PR 描述按模板填写：关联 Issue、改动说明、影响范围、自检清单；
3. `CODEOWNERS` 会自动指派该目录的负责人评审；
4. CI 必须全绿（ruff + pytest + 启动冒烟）才能合并；
5. 合并方式用 **Squash merge**，保持 `main` 线性历史，便于按提交统计贡献；
6. 评审意见用 `Request changes` 记录，修复后回复评论再 re-request review——这些都能作为过程佐证。

## 6. 冲突处理约定

| 冲突类型 | 处理方式 |
|---|---|
| 同时改了 `app/core/*` | 公共基础由组长裁决，组员提 PR 说明需求，由组长实现 |
| 同时新增表 | 各域独立表名加域前缀（`trace_*` / `trade_*`），互不改对方的 `models.py` |
| 同时改 `main.py` 注册路由 | 各自只新增一行 `app.include_router(...)`，冲突时保留双方 |
| 数据库结构变更 | 必须附 `sql/` 下的变更脚本与回滚说明，评审通过后执行 |
