# 数据库设计（溯源链域与公共基础）

> 完整 13 张表见报告表 4-3；本文只覆盖组长负责的 6 张表与相关约定。
> 生产 DDL：`sql/schema_mysql.sql`；开发环境由 SQLAlchemy `create_all` 自动建表。

## 1. 设计约定

| 约定 | 说明 | 落地方式 |
|---|---|---|
| 主键 | 32 位字符串雪花号，前缀标识实体 | `app/core/ids.py::new_id` |
| 审计字段 | 所有表带 `created_at` / `updated_at` | `TimestampMixin` |
| 溯源记录只追加 | `trace_event` 不提供 UPDATE / DELETE | 无更新接口 + MySQL 只授 `SELECT, INSERT` |
| 时间口径 | 存 naive UTC，秒精度 | `normalize_time` |
| 金额与产量 | `DECIMAL(10,2)` | `Numeric(10, 2)` |

## 2. 表清单

| 表名 | 中文名 | 所属域 | 说明 |
|---|---|---|---|
| sys_user | 用户表 | 用户与运营域 | 账号、口令摘要、角色 |
| farm | 产地（农场）表 | 用户与运营域 | 名称、地址、面积、认证状态 |
| batch | 生产批次表 | 溯源链域 | 地块、品种、播种/采收、链尾锚点 |
| trace_event | 溯源环节记录表 | 溯源链域 | 环节、操作人、前后哈希 |
| trace_code | 溯源码表 | 溯源链域 | 码值、码类型、状态 |
| scan_log | 扫码日志表 | 溯源链域 | 码值、时间、地域、设备 |

## 3. 核心表结构

### 3.1 batch（生产批次）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| batch_id | VARCHAR(32) | PK | 批次标识 |
| batch_no | VARCHAR(32) | UNIQUE | 对外批次号 `PC-YYYYMMDD-XXXX` |
| farm_id | VARCHAR(32) | FK → farm | 所属产地 |
| crop_name | VARCHAR(64) | NOT NULL | 品种 |
| plot_no | VARCHAR(32) | NOT NULL | 地块编号 |
| plant_date | DATE | NOT NULL | 播种日期 |
| harvest_date | DATE | NOT NULL，≥ plant_date | 采收日期 |
| expected_yield | DECIMAL(10,2) | NULL | 预计产量 |
| status | VARCHAR(16) | NOT NULL | draft/growing/harvested/qualified/closed |
| event_count | INT | NOT NULL DEFAULT 0 | **链尾序号锚点** |
| last_event_hash | CHAR(64) | NULL | **链尾摘要锚点** |

索引：`UNIQUE(farm_id, plot_no, crop_name, harvest_date)`（防重复建档）、`idx_batch_farm`、`idx_batch_status`。

### 3.2 trace_event（溯源环节）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| event_id | VARCHAR(32) | PK | 记录标识 |
| batch_id | VARCHAR(32) | FK → batch | 所属批次 |
| seq_no | INT | `UNIQUE(batch_id, seq_no)` | 批次内序号，从 1 递增 |
| stage | VARCHAR(16) | NOT NULL | 五类环节 |
| operator_id | VARCHAR(32) | NOT NULL | 操作人 |
| occurred_at | DATETIME | NOT NULL | 环节发生时间 |
| location | VARCHAR(128) | NULL | 发生地点（**未参与摘要**，见 §5） |
| detail | TEXT | NOT NULL | 规范化 JSON |
| prev_hash | CHAR(64) | NOT NULL | 前一条摘要，首条为创世摘要 |
| curr_hash | CHAR(64) | NOT NULL | 本条 SHA-256 |

**索引选择的理由**：`UNIQUE(batch_id, seq_no)` 不只是查询加速，它是并发写入的**正确性兜底**——
两个请求抢到同一序号时，第二个必然插入失败并回滚重试，不会产生两条 `seq_no` 相同的记录。

### 3.3 trace_code（溯源码）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| code_id | VARCHAR(32) | PK | 码标识 |
| code_value | VARCHAR(64) | UNIQUE | `批次号-ITM0001` 形式 |
| code_type | VARCHAR(8) | NOT NULL | box / item |
| batch_id | VARCHAR(32) | FK → batch | 所属批次 |
| item_no | INT | NOT NULL | 批次内序号 |
| status | VARCHAR(16) | NOT NULL | active / revoked |
| revoked_at / revoked_reason | DATETIME / VARCHAR(128) | NULL | 作废留痕 |

### 3.4 scan_log（扫码日志）

`log_id` PK、`code_value`、`batch_id`、`user_id`、`scanned_at`、`province`、`city`、`device`、`ip`。
索引：`idx_scan_code`、`idx_scan_batch(batch_id, scanned_at)`（支撑"某批次最近扫码"与跨区异常判断）。

## 4. 实体关系

```
sys_user 1 ──── n farm 1 ──── n batch 1 ──── n trace_event
                                  │
                                  ├── n trace_code
                                  └── n scan_log
```

- 用户 → 产地：一对多（一个农户可有多块产地）；
- 产地 → 批次：一对多，按 `farm_id + plot_no + crop_name + harvest_date` 唯一；
- 批次 → 环节记录：一对多，`seq_no` 递增，链式摘要串联；
- 批次 → 溯源码：一对多，箱码与单品码分别编号；
- 批次 → 扫码日志：一对多，供运营洞察与异常判断。

## 5. 哈希口径与已知缺口

```
prev_hash(1) = SHA-256("GENESIS" | batch_id)
curr_hash(n) = SHA-256(prev_hash | batch_id | seq_no | stage | operator_id | occurred_at | detail)
```

参与摘要的字段：`prev_hash`、`batch_id`、`seq_no`、`stage`、`operator_id`、`occurred_at`（秒精度）、`detail`（规范化 JSON）。

**不包括 `location`**——这与报告表 4-4 的公式保持一致，但意味着只改地点不会被检测到。
演进方案（v1.1）：把 `location` 纳入摘要，并写数据迁移脚本重算全量 `curr_hash`；
由于链上已有历史数据，迁移必须整批重算并保留迁移前后摘要快照，属于破坏性变更，需在迭代评审确认后执行。

**另一处边界**：单机哈希链无法防止"整条链被重算"——攻击者若能改库，也能把全部摘要重算一遍。
真正的防篡改需要外部锚定：定期把 `(batch_id, event_count, last_event_hash)` 写入第三方存证或区块链，
校验时比对锚点。当前实现已把这两个字段落库，为后续接入留好接口。

## 6. 只追加约束的落地

| 层次 | 措施 |
|---|---|
| 接口层 | 不提供 `trace_event` 的 PUT/PATCH/DELETE 路由 |
| 服务层 | `TraceService` 无更新方法，仅 `append_event` / `verify_batch` |
| 数据库 | 生产账号只授 `SELECT, INSERT`（`sql/schema_mysql.sql` 末尾） |
| 测试 | `tests/test_chain.py` 模拟直接改库，验证校验能定位 |

唯一例外：`trace_code.status` 的人工作废需要 UPDATE，已用列级授权限定为
`status, revoked_at, revoked_reason, updated_at` 四列，并记录原因与时间。

## 7. 从 SQLite 切 MySQL

1. `.env` 中改 `DATABASE_URL=mysql+pymysql://user:pwd@host:3306/agritrace?charset=utf8mb4`；
2. `pip install pymysql`（或 `mysqlclient`）；
3. 执行 `sql/schema_mysql.sql` 建表，按需授予只追加权限；
4. 业务代码无需修改——差异只在引擎连接参数与 `HashChain.append` 的行锁语义（MySQL 走 InnoDB 行锁，SQLite 走库级写锁）。
