## 4. 关键用例设计思路

### 4.1 篡改检测（最重要）

不是"跑一遍正常流程返回 ok"，而是**直接改库**再校验：

```python
db.execute(text("UPDATE trace_event SET detail = :d WHERE event_id = :id"), ...)
result = HashChain.verify(db, batch_id)
assert result.reason == "content_tampered"
assert result.broken_at == 2          # 精确定位到出问题的序号
```

覆盖四种破坏方式：改内容、改 `prev_hash`、删中间记录、删尾部记录并同步篡改计数。
其中尾部截断只有依靠 `batch.event_count` / `last_event_hash` 锚点才能发现，是设计上的关键补强。

### 4.2 并发（报告 5.3.1 的复现）

用文件型 SQLite（内存库单连接无法模拟竞争），6 个线程各开独立会话，
通过 `Barrier` 同时开始，每个线程追加 2 条：

```python
assert [e.seq_no for e in events] == list(range(1, 13))
assert HashChain.verify(db, batch_id).ok is True
```

该用例是对"`SELECT MAX(seq_no)+1` 会产生重复序号"这一缺陷的回归保护。

### 4.3 权限与越权

- 农户访问他人批次 → 403；
- 农户调用 UC-05 校验接口 → 403（该用例只对运营/监管开放）；
- 消费者建档 → 403；匿名建档 → 401。

### 4.4 幂等

同一赋码请求连续提交两次，断言返回的码值列表完全相同，且码表总数不增加。
这对应报告 5.2.1 中"批量赋码未做幂等，重复提交生成重复码值"的人工修改点。

## 6. 性能基准

`python scripts/bench.py 5000`（本机 Windows / SQLite / 单进程）：

| 指标 | 实测 | 报告 3.6 目标 | 结论 |
|---|---|---|---|
| 5000 条记录链校验 | **0.055 s** | < 2 s | ✅ 达标 |
| 单码扫码查询（含整链校验）均值 | **123.2 ms** | — | — |
| 单码扫码查询 P95 | **138.4 ms** | < 500 ms | ✅ 达标 |
| 5000 条记录构造写入 | 0.14 s | — | 仅作参考 |

说明：

- 扫码查询比单独校验慢，是因为要组装时间轴、查询产地与操作人姓名并做脱敏，
  其中 `scan_log` 写入也计入；优化方向是给 `(batch_id, seq_no)` 之外再加投影查询，避免拉全字段。
- 上述是 SQLite 单机数据，**MySQL + 100 并发**的指标尚未实测，已在 Issue #20 中跟踪，
  报告中不应把本地数据写成生产结论。
