# 数据库设计（交易域）

交易域在报告表 4-3 的 13 张表中占 5 张：`product`、`orders`、`order_item`、`payment`、`review`。
建表脚本见 `sql/schema_trade.sql`，ORM 定义见 `app/trade/models.py`，两者字段一一对应。

## 1. 表清单与职责

| 表名 | 中文名 | 职责 | 关键约束 |
|---|---|---|---|
| `product` | 商品表 | 一行 = 一个可售 SKU（产地 + 批次 + 规格） | `(farm_id, batch_id, title, spec)` 唯一 |
| `orders` | 订单主表 | 订单头，一单一产地，金额与状态 | `order_no` 唯一 |
| `order_item` | 订单明细 | 商品快照（标题/规格/单价/小计） | 外键 `order_id` |
| `payment` | 支付流水 | 委托支付的结果与重试次数 | **`order_id` 唯一**（BR-04） |
| `review` | 评价表 | 收货后的评分与文字 | `(order_id, product_id)` 唯一 |

继承公共基础层的三条约定：主键为 32 位雪花字符串（业务前缀 `PRD/ORD/OIT/PAY/REV`）、
所有表带 `created_at` / `updated_at`、金额一律 `DECIMAL(10,2)` 不使用浮点。

## 2. 四个关键设计决策

### 2.1 为什么没有 `cart` 表

报告 4.5 的 13 张表里没有购物车，`orders.farm_id` 又要求一单一产地。若新增 `cart` 表，
一是总数变成 14 张与报告不符，二是「购物车跨产地」的合并/拆分逻辑要在库里再维护一遍。

因此购物车放在浏览器 `localStorage`，下单时才提交 `[{product_id, quantity}]`，
由服务端按 `farm_id` 分组拆单。好处：表结构简单、金额同源（页面金额来自同一套服务端计算）；
代价：换设备购物车不跟随、无法做「购物车降价提醒」。这两点已写入演进说明，属于有意识的取舍。

### 2.2 一个订单只对一个产地

`orders.farm_id` 非空，购物车跨产地时拆成多笔订单。这条约束同时解决三件事：

1. 农户只能看到并处理自己产地的订单（`scope=sales` 的过滤条件）；
2. 运费按产地分别计算，不会出现「两个产地合并凑单免邮」的争议；
3. 报告要求的「按产地统计交易额」直接对 `orders.farm_id` 分组即可，不用穿透明细聚合。

### 2.3 `payment.order_id` 唯一：把并发问题交给数据库

报告 BR-04 要求同一订单只允许一条成功流水。应用层写 `if exists: return` 只能挡住顺序请求，
并发下两个请求会同时通过判断。这里改为在 `order_id` 上建唯一索引：

- 第一笔 INSERT 成功；
- 第二笔触发 `IntegrityError`，Service 捕获后回滚并按幂等返回既有流水。

失败重试不新增行，而是更新同一行的 `attempt_count` / `fail_reason`，
这样既保留「最多重试 3 次」的计数，也不会让流水表堆满噪声行。

### 2.4 取消/超时都用「加库存」而不是「改库存」

`BR-06` 规定库存只允许通过状态流转释放。取消与超时取消走同一条路径：

```sql
UPDATE product SET stock = stock + :n WHERE product_id = :pid;
```

不做 `SET stock = :fixed_value`，避免与并发的下单请求互相覆盖。

## 3. 核心 SQL

下单扣减（`affected_rows == 0` 即失败，整笔事务回滚）：

```sql
UPDATE product
   SET stock = stock - :n
 WHERE product_id = :pid
   AND status = 'on_shelf'
   AND stock >= :n;
```

支付成功后累加销量：

```sql
UPDATE product SET sales = sales + :n WHERE product_id = :pid;
```

查询超时未支付订单（后台任务每 60 秒执行）：

```sql
SELECT * FROM orders
 WHERE status = 'pending'
   AND created_at < :cutoff
 LIMIT 200;
```

## 4. 索引与容量预估

| 索引 | 用途 |
|---|---|
| `product(status, price)`、`product(farm_id)` | 检索筛选与农户自看列表 |
| `orders(buyer_id, created_at)` | 「我买到的」按时间倒序分页 |
| `orders(farm_id, status)` | 农户「待发货」列表 |
| `payment(order_id)` 唯一 | 幂等与防重复流水 |
| `review(product_id, created_at)` | 商品详情页评价列表 |

课程演示量级（万级订单）下上述索引足够；若订单上百万，`orders` 按 `created_at` 做月度分区，
`payment` / `review` 按 `order_id` 前缀分片是下一步演进方向，不影响当前代码结构。

## 5. 与溯源域的衔接

- `product.batch_id` 指向 `batch.batch_id`，商品详情页据此展示批次号、地块、采收日期与链上环节数；
- `order_item.batch_id` 是下单时的批次快照，`review.batch_id` 复制自明细，支撑「按批次看口碑」；
- 交易域**只读**溯源表，不写 `trace_event`：销售的环节记录由溯源域的 `Stage.SALES` 负责，
  两个域通过 `batch_id` 关联而不是互相调用写接口。
