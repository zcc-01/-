# UC-02 录入溯源环节

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-02 |
| 用例名称 | 录入溯源环节 |
| 参与者 | 农户（主要） |
| 所属业务域 | 溯源链域 |
| 负责人 | 张×× |
| 对应接口 | `POST /api/batches/{batch_id}/events` |
| 关联需求 | 表 2-3「溯源管理 / 环节录入」，优先级 M；扩展用例 UC-14 |

## 前置条件

1. 农户已登录且为该批次所属产地的所有者；
2. 批次存在且未结批（`status != closed`）；
3. 环节类型属于 `production / processing / quality / logistics / sales` 五类之一。

## 后置条件

1. 新增一条 `trace_event`，`seq_no` 为当前批次链尾序号 +1；
2. `prev_hash` 等于上一条记录的 `curr_hash`（首条为创世摘要）；
3. 批次 `event_count` 与 `last_event_hash` 同步更新；
4. 返回该记录的序号、摘要与可能的预警提示。

## 基本流程

1. 农户选择批次，填写环节类型、发生时间、地点与明细（如检测报告编号、结论）；
2. 前端提交到 `POST /api/batches/{batch_id}/events`；
3. 系统校验登录态、角色与产地归属；
4. 系统校验批次状态与环节类型；
5. 系统比对本次发生时间与上一条记录时间，若倒挂则生成预警提示（不阻断）；
6. 系统原子占用序号，计算 `curr_hash`，写入记录并更新链尾锚点；
7. 系统提交事务，返回记录详情与 `warning` 字段。

## 异常流程

| 编号 | 触发条件 | 系统响应 |
|---|---|---|
| 3a | 非本人批次 | 403 |
| 4a | 批次已结批 | 422，`code = 42201`「批次已结批，不能再追加溯源记录」 |
| 4b | 环节类型非法 | 422，`code = 40001` |
| 4c | 明细超过 4000 字符 | 422，参数校验失败 |
| 5a | 发生时间早于上一条记录 | 200 但返回 `warning`，记录照常上链（交运营域生成工单） |
| 6a | 并发写入撞上唯一索引 | 回滚后自动重试，最多 5 次；仍失败返回 503、`code = 50002` |

## 业务规则

- **BR-05** 溯源记录只允许追加，不提供修改与删除接口；数据库账号对 `trace_event` 不授予 `UPDATE / DELETE`；
- **BR-06** 序号分配必须在数据库层完成（批次行 `event_count` 原子自增），不使用应用层锁，以支持多 worker 部署；
- **BR-07** 时间倒挂属于「可疑但可能真实」的情况（如补录），一律先记录再预警，避免为了校验而丢失现场数据；
- **BR-08** 同一条记录的 `occurred_at` 统一截断到秒并以 UTC 参与摘要计算，保证跨机器重算一致。

## 验收用例

| 用例 | 预期 |
|---|---|
| 追加加工环节 | 200，`seq_no = 2`，`prev_hash` 等于上一条 `curr_hash` |
| 追加时间倒挂的环节 | 200，返回 `warning`，链仍完整 |
| 已结批批次追加 | 422 |
| 非法环节类型 | 422 |
| 6 线程并发追加 12 条 | 序号 1~13 连续，链校验通过 |
