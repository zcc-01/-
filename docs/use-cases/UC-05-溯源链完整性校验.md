# UC-05 溯源链完整性校验

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-05 |
| 用例名称 | 溯源链完整性校验 |
| 参与者 | 平台运营（主要）、监管人员（次要） |
| 所属业务域 | 溯源链域 |
| 负责人 | 张×× |
| 对应接口 | `GET /api/batches/{batch_id}/verify` |
| 关联需求 | 表 2-3「溯源管理 / 完整性校验」，优先级 S；被 UC-04 包含调用 |

## 前置条件

1. 调用方已登录，角色为 `operator` 或 `regulator`；
2. 目标批次存在。

## 后置条件

1. 返回校验结论 `ok`、记录总数与期望总数；
2. 若断链，返回 `broken_at`（出问题的 `seq_no`）、`reason` 与 `broken_event_id`；
3. 不修改任何业务数据（纯读 + 重算）。

## 基本流程

1. 运营在批次详情页点击「完整性校验」；
2. 系统按 `seq_no` 升序、每批 500 条流式读取该批次的全部记录；
3. 系统以 `SHA-256("GENESIS"|batch_id)` 作为链首基准；
4. 逐条重算 `curr_hash` 并与库中值比对，同时校验 `prev_hash` 是否等于上一条 `curr_hash`；
5. 系统校验记录总数与批次锚点 `event_count`、链尾摘要与 `last_event_hash` 是否一致；
6. 全部通过则返回 `ok = true`，否则在首个异常处立即返回定位结果。

## 异常流程

| 编号 | 触发条件 | 定位结果 |
|---|---|---|
| 4a | 某条记录内容被改动 | `reason = content_tampered`，`broken_at` = 该条 `seq_no` |
| 4b | `prev_hash` 与上一条 `curr_hash` 不一致 | `reason = prev_hash_mismatch` |
| 4c | 序号不连续（中间记录被删除） | `reason = seq_gap`，`broken_at` = 缺失位置 |
| 5a | 记录总数少于锚点 | `reason = count_mismatch` |
| 5b | 尾部记录被删且锚点被同步篡改 | `reason = tail_truncated` |
| 3a | 批次不存在 | 404 |
| 3b | 农户调用 | 403（UC-05 只对运营与监管开放） |

## 业务规则

- **BR-14** 校验以**返回值**表达结论，不抛异常；因为 UC-04 需要在展示记录的同时提示异常；
- **BR-15** 分批流式读取（默认 500 条/批），避免 5000 条以上记录一次性进入内存；
- **BR-16** 校验必须从链首开始逐条重算，不能只比对首尾摘要——否则中间篡改无法发现；
- **BR-17** 性能目标：单码查询 P95 < 500 ms，5000 条记录的链路校验 < 2 s（报告 3.6）。

## 校验结果示例

```json
{
  "code": 0,
  "data": {
    "batch_id": "BAT...",
    "ok": false,
    "total": 2,
    "expected_total": 3,
    "broken_at": 2,
    "reason": "content_tampered",
    "broken_event_id": "EVT...",
    "message": "第 2 条记录校验失败：记录内容与摘要不一致，疑似字段被篡改",
    "checked_at": "2026-11-19T14:20:00+08:00"
  }
}
```

## 验收用例

| 用例 | 预期 |
|---|---|
| 正常链 | `ok = true`，`total` 与 `expected_total` 相等 |
| 改 `detail` 字段 | `ok = false`，`reason = content_tampered`，`broken_at` 精确 |
| 改 `prev_hash` | `reason = prev_hash_mismatch` |
| 删中间记录 | `reason = seq_gap` |
| 农户调用 | 403 |
| 监管调用 | 200 |
