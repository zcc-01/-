# UC-03 生成溯源码

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-03 |
| 用例名称 | 生成溯源码（一物一码赋码） |
| 参与者 | 农户（主要） |
| 所属业务域 | 溯源链域 |
| 负责人 | 张×× |
| 对应接口 | `POST /api/batches/{batch_id}/codes`、`GET /api/batches/{batch_id}/qrcodes.zip` |
| 关联需求 | 表 2-3「溯源管理 / 一物一码赋码」，优先级 M |

## 前置条件

1. 农户已登录且为该批次所属产地的所有者；
2. 批次已采收（`status ∈ {harvested, qualified}`）——未采收的批次不允许赋码，避免"预计产量"被当作实物赋码；
3. 单次赋码数量在 1～5000 之间（报告 1.2 分目标：单批次不少于 5000 个单品）。

## 后置条件

1. 按需生成 `trace_code` 记录，码值为 `{batch_no}-{ITM|BOX}{四位序号}`；
2. 同一批次、同一码类型的码值唯一，重复提交不产生重复码；
3. 可导出 ZIP 包，内含每个码的 PNG 二维码与 `manifest.csv` 清单。

## 基本流程

1. 农户在批次详情页选择码类型（批次码 / 单品码）与数量；
2. 前端提交到 `POST /api/batches/{batch_id}/codes`；
3. 系统校验登录态、产地归属、批次状态与数量上限；
4. 系统按序号 1..N 派生码值，查询已存在的序号，仅插入缺失部分；
5. 系统提交事务并返回 1..N 的完整码列表；
6. 农户点击「导出二维码」，系统按码值生成扫码链接 `{base_url}/trace/{code}` 并打包返回。

## 异常流程

| 编号 | 触发条件 | 系统响应 |
|---|---|---|
| 3a | 批次未采收 | 422，「批次采收后才允许赋码」 |
| 3b | 数量为 0 或超过 5000 | 422，参数校验失败 |
| 4a | 并发赋码撞上 `code_value` 唯一索引 | 回滚并返回 409「赋码冲突，请重试」 |
| 6a | 导出数量超过上限 | 422，`limit ≤ 5000` |

## 业务规则

- **BR-09** 码值由批次号与序号**确定性派生**，不使用随机串：既能幂等去重，也便于人工核对包装与批次；
- **BR-10** 同一批次内单品码与批次码分别独立编号，互不占用序号；
- **BR-11** 赋码前必须校验批次状态，避免"未采收即赋码"造成超卖与虚假溯源；
- **BR-12** 作废码不物理删除，只把 `status` 置为 `revoked` 并记录原因与时间（唯一允许的更新，留痕可审计）。

## 验收用例

| 用例 | 预期 |
|---|---|
| 采收后赋码 5 个 | 200，码值 `...-ITM0001` ~ `...-ITM0005` |
| 重复提交相同请求 | 返回同一组码值，总数不变 |
| 未采收即赋码 | 422 |
| 数量 5001 | 422 |
| 作废后扫码 | 410，`code = 42202` |
| 导出二维码 | 200，zip 内含 3 张 PNG + manifest.csv |
