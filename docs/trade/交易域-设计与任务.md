## 一、需求本质

表面需求是「做个商城」，真正的工程问题有三个：

1. **不能超卖。** 库存是多人竞争的共享数据，任何「先查再改」的写法都会在并发下出错；
2. **不能重复收钱。** 支付按钮会被连点、网络会重试，同一订单必须只产生一条成功流水；
3. **金额不能被客户端左右。** 前端传来的价格一律不可信，必须服务端重算。

这三个问题都不是「功能有没有」的问题，而是「功能对不对」的问题，也正好是本项目要体现的软件工程内容：
状态机、事务边界、并发控制、幂等设计。

## 三、方案权衡

### 3.0 与溯源域的边界

交接文档约定的跨域契约是「下单前查 `trace_code.status == active`」。落地方式：
商品若绑定批次，先统计该批次的码数量——**没有码不拦**（建批后赋码是后续流程，拦了会误伤新品），
**有码但全部作废则拒单**（说明批次出了质量事故，平台必须停售）。交易域只读 `trace_code`，不写溯源表。

### 3.1 购物车：服务端表 vs 前端本地

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 新建 `cart` 表 | 换设备同步、可做降价提醒 | 表数变 14 张与报告不符；跨产地合并拆分逻辑要在库里再维护一遍 |
| **B. 前端 localStorage + 下单时提交明细（采用）** | 表结构与报告一致；金额只有一处计算 | 购物车不跟随设备；无法做离线提醒 |

取舍理由：课程项目的验收标准是「13 张表 + 5 个交易用例」，方案 B 用更小的结构满足了功能，
把复杂度留在真正需要严谨的地方（下单事务）。这也是报告中「设计取舍」一节的素材。

### 3.2 库存：应用层判断 vs 数据库条件更新

| 方案 | 结果 |
|---|---|
| A. `SELECT stock` → `if stock >= n` → `UPDATE stock = 新值` | 并发下 100 件卖出 137 单（报告 5.3.2 第 1 轮的真实结果） |
| B. Python 里加锁后写回 | 单进程有效，多 worker 失效，且读到旧值仍会错 |
| **C. `UPDATE ... WHERE stock >= n` + 判断 affected_rows（采用）** | 由数据库行锁保证原子性，`affected_rows = 0` 即失败并回滚 |

### 3.3 重复支付：应用层判断 vs 唯一索引

应用层 `if exists: return` 只能挡住顺序请求；并发下两个请求会同时通过判断。
最终采用「`payment.order_id` 唯一索引 + 捕获 `IntegrityError` 后幂等返回」，
把正确性交给数据库，应用层只负责把冲突翻译成用户能懂的返回。

### 3.4 超时取消：定时任务选型

| 方案 | 说明 |
|---|---|
| 引入 APScheduler / Celery | 功能完整，但为一次每分钟的扫描多装一个组件与一个 broker |
| **asyncio 后台任务 + `asyncio.to_thread`（采用）** | 零新增依赖，单机部署足够；多实例下退化为「谁扫到谁处理」，依赖状态判断保证幂等 |
| 只在支付时惰性判断 | 用户视角正确，但没人访问的僵尸订单会长期占住库存 |

最终采用「惰性过期（支付/查询时判断）+ 定时兜底（每 60 秒）」两层。

## 四、结构设计

```
app/trade/
├── models.py    实体与状态机常量（ProductStatus / OrderStatus / PaymentStatus / TradeRule）
├── schemas.py   出入参（Pydantic v2），金额与库存不接受前端结论
├── gateway.py   模拟支付网关（无数据库依赖，供事务外调用）
├── service.py   ProductService / OrderService / ReviewService，事务边界在此
└── router.py    接口层，只做参数校验、鉴权与响应包装
```

类职责与报告表 4-2 的口径一致：`OrderService` 是控制类，编排下单、支付、取消三段流程；
`Product` / `Order` / `OrderItem` / `Payment` / `Review` 是实体类；
`MockPayGateway` 属于基础设施组件（对应报告中的 `gateway` 属性）。

前端：`app/web/templates/{shop,product,cart,orders}.html` + `app/web/static/shop.js`，
页面只渲染骨架，数据全部来自 `/api`，保证「页面金额」与「服务端金额」同源。

## 六、风险预演（上线后最可能挂在哪）

| 风险 | 触发场景 | 应对 |
|---|---|---|
| 库存被死单占住 | 用户下单后不支付 | 30 分钟惰性过期 + 每 60 秒兜底清理 |
| 支付回调重复处理 | 网关重试通知 | `payment.order_id` 唯一索引 + 幂等返回 |
| 订单金额与页面不一致 | 加购后农户改价 | 下单以服务端当前价重算，试算仅作提示 |
| 商品下架导致下单失败 | 结算页停留过久 | 条件更新带 `status = 'on_shelf'`，失败信息精确到具体商品 |
| 销量口径被污染 | 未支付订单计入销量 | 销量只在支付成功后累加 |
| SQLite 写锁超时 | 并发压测 | WAL + `busy_timeout=30s`；生产切 MySQL 即消失 |

## 十、本地运行与录屏建议

```bash
pip install -r requirements.txt
python -m app.db.seed                     # 建表 + 演示数据
python -m uvicorn app.main:app --port 8000
```

随后打开：

- `/shop` —— 列表与筛选（图 5-5 左半的素材）
- `/shop/{id}` —— 详情与批次溯源信息
- `/cart` —— 购物车与结算（图 5-5）
- `/orders` —— 支付/发货/收货/评价（图 5-6）

演示账号：`consumer01` / `farmer01`，口令 `Passw0rd!`。建议录屏顺序：
加购 → 结算 → 支付成功 → 用 farmer01 登录发货 → 换回 consumer01 确认收货 → 评价 → 商品详情出现评价。
