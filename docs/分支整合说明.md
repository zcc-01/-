# 三分支整合说明

> 本文对应任务：「分析 `main` / `feat/trace-chain` / `feat/trade` / `feat/identity-ops` 的功能与依赖，
> 整合为一个可运行系统，说明入口、边界、调用关系，并给出冲突处理与验证结果」。
> 所有结论基于 `git ls-tree`、`git diff` 与本地可运行验证，不是推测。

---

## 1. 分支现状：一个必须先说清的事实

| 分支 | HEAD 提交 | 文件数 | 实际内容 |
|---|---|---|---|
| `main` | 初始提交 | 1 | 只有 `README.md` |
| `feat/trace-chain` | 组长交付 | 70+ | 溯源链域 + 公共基础 + 测试 + 文档 |
| `feat/trade` | 与 `main` 相同 | 1 | **只有 `README.md`，零代码** |
| `feat/identity-ops` | 与 `main` 相同 | 1 | **只有 `README.md`，零代码** |

验证命令与结果：

```bash
$ git ls-tree -r --name-only origin/feat/trade
README.md
$ git diff --stat origin/main..origin/feat/trade
# 无输出 —— 与 main 完全一致
```

因此「三个分支互相合并」在原始状态下**不成立**：没有可合并的对方代码。
本整合分支的工作实质是：**以 `feat/trace-chain` 为基线，补齐另外两个业务域，并把三域接成一条链路**，
分支结构保持与报告的分工表一致（每人一条域分支，最终由 `feat/integrate` 汇总）。

## 2. 三个业务域的功能边界

| 业务域 | 用例 | 负责目录 | 核心产物 |
|---|---|---|---|
| 溯源链域 | UC-01～UC-05 | `app/trace/` | 批次建档、环节上链（哈希链）、赋码、扫码聚合、完整性校验 |
| 交易域 | UC-06～UC-10 | `app/trade/` | 商品上架、检索筛选、购物车、下单支付、发货收货、评价 |
| 用户与运营域 | UC-11～UC-15 | `app/account/` `app/ops/` | 登录鉴权、产地认证审核、经营看板、异常预警、监管回溯 |
| 公共基础 | — | `app/core/` `app/db/` `app/common/` `app/web/` | 统一响应、错误码、JWT、雪花主键、会话、模板骨架 |

**共同点**（三域一致遵循的约定）

1. 统一响应体 `{code, message, data}`，异常由 `app/core/errors.py` 统一转 HTTP 状态；
2. 统一主键：32 位字符串雪花 ID（`app/core/ids.py`），避免三域并行开发主键冲突；
3. 统一时间与落库：`TimestampMixin` + UTC naive 存储，展示层再本地化；
4. 统一页面骨架 `base.html`，样式全部走 `app/web/static/style.css` 的 CSS 变量；
5. 统一分层：`router`（协议/鉴权）→ `service`（业务规则）→ `models`（持久化），不跨层直连。

**差异点**

| 维度 | 溯源链域 | 交易域 | 用户与运营域 |
|---|---|---|---|
| 一致性要求 | 强一致（哈希链不许断） | 强一致（不许超卖） | 最终一致（审核/预警可异步处置） |
| 并发热点 | 同批次追加环节（串行序号） | 同商品扣库存（条件更新） | 同产地重复提交（唯一在途） |
| 外部依赖 | 无 | 支付网关（已抽象为可替换接口） | 无 |
| 失败策略 | 校验失败仍返回履历 + 告警 | 失败整单回滚 | 预警建单失败只记日志 |

## 3. 依赖关系：三域之间只有 4 个真实耦合点

```
                 ┌──────────────────────────────┐
                 │        公共基础 app/core      │
                 │  response / errors / security │
                 │  ids / deps / config          │
                 └───────▲──────────▲───────────┘
                         │          │
        ┌────────────────┘          └───────────────┐
        │                                           │
┌───────┴────────┐        ┌────────────────┐  ┌──────┴──────────┐
│  app/trace     │        │  app/trade     │  │  app/ops        │
│  溯源链域       │        │  交易域         │  │  用户与运营域    │
└───┬────────┬───┘        └───┬────────┬───┘  └───┬─────────┬───┘
    │        │                │        │          │         │
    │        └────────────────┼────────┼──────────┘         │
    │  ①断链预警              │ ③批次可售校验 ④认证打标        │
    │  ②时间倒挂预警          │                              │
    └──────────────► app/ops/alerting ◄──────────────────────┘
                     （只依赖 ops.models，无反向依赖）
```

| # | 方向 | 触发点 | 实现位置 | 为什么这样切 |
|---|---|---|---|---|
| ① | 溯源 → 运营 | 扫码校验发现断链，自动开预警单 | `trace/service.py::_safe_raise_chain_alert` | 预警建单独立事务 + 吞异常，保证「扫码不因预警失败而 500」 |
| ② | 溯源 → 运营 | 环节时间倒挂，录入成功但开预警单 | `trace/service.py::add_event` | 报告要求「不阻断录入、只提示复核」 |
| ③ | 交易 → 溯源 | 上架校验批次已采收；下单再次校验未结批/未封存 | `trade/service.py::_assert_sellable_batch`、`OrderService.create` | 商品不能凭空存在，也不能卖出已封存的货 |
| ④ | 运营 → 交易 | 认证通过后给该产地全部商品打认证标识 | `ops/service.py::CertService.review` | 报告 UC-12 步骤 7 的显式要求 |

**防循环依赖的关键设计**：预警单被拆到 `app/ops/alerting.py`，只依赖 `ops.models` 与 `core`，
不 import `trace` / `trade`。否则 `trace → ops → trace` 会形成 import 环。
验证：`python -c "import app.trace.service, app.ops.service, app.trade.service"` 正常。

## 4. 系统入口与调用关系

### 4.1 唯一进程、两类入口

| 入口 | 前缀 | 呈现 | 鉴权 |
|---|---|---|---|
| API | `/api/**` | JSON（37 条路径 / 47 个操作） | `Authorization: Bearer <JWT>` |
| 页面 | `/`、`/shop`、`/cart`、`/orders`、`/console`、`/trace/{code}` | Jinja2 服务端渲染 | HttpOnly Cookie 承载同一个 JWT |
| 文档 | `/docs` | Swagger UI | 无 |

两条入口**共用同一套 service 层**：页面里不写业务规则，只做参数收集与渲染。
这样不会出现「接口改了口径、页面还是旧算法」的双份实现。

### 4.2 应用装配顺序（`app/main.py`）

```python
app.include_router(account_router)   # /api/auth    登录鉴权
app.include_router(trace_router)     # /api/...     溯源链域
app.include_router(trade_router)     # /api/...     交易域
app.include_router(ops_router)       # /api/...     用户与运营域
app.include_router(web_router)       # /shop 等     页面
```

启动时 `init_db()` 建表 + `seed_if_empty()` 灌种子，评审者 clone 后无需手工初始化。

### 4.3 一次「扫码 → 下单 → 审核」的完整调用链

```
GET /trace/{code}
  trace.router.trace_page
    → TraceService.scan
        → HashChain.verify            链完整性
        → raise_chain_broken (ops)    断链则开预警单
    → render("scan.html")

POST /cart/checkout
  web.router.checkout
    → OrderService.create
        → Batch 状态校验（跨域读溯源域）
        → _deduct_stock（条件 UPDATE，扣不动即回滚）
    → 303 重定向 /orders

POST /console/certs/{id}/review
  web.router.console_cert_review
    → CertService.review
        → BR-08 结论不可改校验
        → farm.cert_status = approved
        → UPDATE product SET certified = 1（跨域写交易域）
        → audit() 留痕
```

## 5. 合并中的冲突与不兼容问题（实际处理记录）

| 问题 | 现象 | 处理方式 |
|---|---|---|
| 分支内容为空 | `feat/trade` / `feat/identity-ops` 与 main 无差异 | 不伪造合并；以 `feat/trace-chain` 为基线补齐两域，新增 `feat/integrate` 汇总 |
| 主键策略冲突风险 | 三域各自 `autoincrement` 会撞号 | 统一 32 位字符串雪花 ID，谁先写谁占号，天然不冲突 |
| 模型注册分散 | 新表不 `import` 就不会建表 | 集中到 `app/models_registry.py`，`conftest` 与启动都只 import 它 |
| 循环导入 | `trace` 要用预警、`ops` 要读溯源 | 拆 `ops/alerting.py` 为只依赖模型的叶子模块 |
| 模板变量冲突 | Jinja2 的 `cart.items` 命中 dict 内置 `.items` 方法，页面 500 | 新增 `app/web/context.py::ns()` 把 dict 递归转 `SimpleNamespace`，API 契约不变 |
| 页面鉴权割裂 | API 用 Bearer，页面没法带 header | 页面登录写 HttpOnly Cookie，同一 JWT 双通道使用，不引入第二套会话 |
| 交易域越权上架 | 农户可上架他人批次 | `ProductService.create` 校验 `farm.owner_id == user.user_id` |
| 支付重复扣款 | 并发/重复点击 | 应用层先查 + 部分唯一索引（只约束成功流水）双保险，失败流水不占位可重试 |
| 监管接口序列化失败 | `scan()` 返回 ORM 对象，`/api/regulator/trace` 500 | 监管侧把 batch 转字典后返回，顺带收敛对外字段 |
| CI 全新克隆启动失败 | `data/` 不存在导致 SQLite 无法建库 | 建库前自动 `mkdir` 父目录；`data/.gitkeep` 随仓库 |
| 中文分类链接 | 未编码的中文 query 被 400 | 模板统一 `|urlencode` |

## 8. 已知缺口（答辩可直接引用）

1. **`location` 字段未参与哈希**：与报告表 4-4 的公式保持一致，故只改「地点」不会被检出。
   v1.1 方案：纳入摘要 + 全量重算迁移（`docs/数据库设计.md` §5）。
2. **支付为本地模拟网关**：`app/trade/payment_gateway.py` 定义了 `Gateway` 抽象，
   接真实渠道只需新增实现并改 `get_gateway()`，业务层零改动。
3. **库存扣减依赖单库条件更新**：单机 SQLite/MySQL 可保证不超卖；
   分库场景需引入分布式锁或库存服务，已在 `docs/设计说明.md` 记录取舍。
4. **页面未接图片上传**：当前用 CSS 色块占位，接口层已具备扩展位（`Product` 无图片字段）。
